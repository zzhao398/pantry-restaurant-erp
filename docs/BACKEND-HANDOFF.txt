PANTRY / PROJECT 1 — FRONTEND TO BACKEND HANDOFF
Prepared 2026-11-09. This is an implementation proposal, not a migration.

CURRENT BOUNDARY
The UI is a client-side demo. Business data is stored in localStorage under
pantry-restaurant-demo-v1. File object URLs exist only for the upload session.
There are no Supabase credentials, live database calls, OCR, POS connections,
customer authentication, real approval permissions, or file storage.
Sites hosting identity is separate from restaurant authorization.
The existing Supabase database was NOT changed by this frontend work.

SOURCE ALIGNMENT
Based on outputs/project1-starter/001_schema.sql (restaurant schema, 12 tables).
Manhattan rice/chicken remain 7000g/3000g; Queens rice/chicken 4000g/0g.
Extra fictional produce, pantry, supplier and menu records enrich the UI.
Dates are moved to a clearly labelled fictional Nov 3-9 sample week.
Mock IDs are readable strings; backend IDs must remain UUIDs.
UI documents embed child lines for display. A real adapter must read/write the
normalized parent/line tables. Every backend write must carry validated brand
and location context, derived from the authenticated user's membership.

PAGE -> EXISTING TABLES / ACTIONS
Overview: aggregate purchase_receipts + lines, sales_batches + lines, stock view.
Inventory: ingredients + locations + inventory_on_hand. History uses movements.
Receiving: purchase_receipts + purchase_receipt_lines + supplier_items.
  Save draft atomically; confirm via post_receipt(UUID). Never insert movements
  from a browser. Supplier item selection must belong to the selected supplier.
  The demo selects ingredients and enters pack conversion manually. The real
  adapter must create/select supplier_items (SKU, ingredient, supplier, pack label)
  and snapshot quantity_per_pack_base; it cannot send the mock lines unchanged.
Daily sales: sales_batches + sales_lines. Confirm via post_sales_batch(UUID).
  UI previews current recipe consumption; server calculates canonical amounts.
Menu: menu_items + recipe_items, shared at brand level. Posted history is immutable.
Suppliers: suppliers + purchase_receipts/lines. No real contact action in demo.
Reports: costs from posted receipt lines, approved invoice totals shown separately.
  These are not gross profit, accounts payable, or inventory valuation reports.

PROPOSED ADDITIONS BEFORE LIVE USE
P0 identity: organization/brand membership, user role and location assignments;
  tested RLS policies, grants and storage access. Current schema has RLS but no
  customer policies or grants. Do not expose it or use a service-role key in UI.
P0 invoice workflow: invoices (brand, location, supplier, original/normalized number,
  dates, currency, subtotal, discounts, tax, shipping, total, status, timestamps),
  invoice_lines (description, quantity, unit, price, ingredient/supplier item mapping),
  invoice_receipt_links, invoice_files (private path, hash, MIME type, size),
  extraction_jobs/results (state, errors, confidence), approval/audit events.
  Demo only has header review. Line extraction, tax validation and approval audit
  are not implemented. Duplicate state is an illustrative sample; real file hashing
  and supplier/number uniqueness belong in backend transactions.
P1 inventory thresholds: location_ingredient_settings (location, ingredient,
  reorder_point_base); category on ingredient or a category lookup.
  Demo threshold is per ingredient and used per location. Approve desired policy.
P1 display fields: menu categories, supplier categories; these are demo-only fields.
P1 traceability: created_by, updated_by, approved_by, created_at, updated_at,
  approved_at and review notes; retain original document revisions and events.
P2 stock adjustments: opening balances, counts, waste, returns, reversals, transfers
  require extending movement types and source constraints, plus atomic RPCs.
P2 recipe versions/effective dates, optional location overrides, yields and modifiers.

PROPOSED ADAPTER CONTRACT (NOT IMPLEMENTED HTTP ROUTES)
listInventory(location_id, search, status) -> normalized stock rows
listMovements(location_id, ingredient_id) -> signed, immutable history
saveReceiptDraft(header, lines, revision) -> receipt UUID; validate SKU ownership
postReceipt(receipt_id, idempotency_key) -> posted/already-posted + latest balances
saveSalesDraft(header, lines, revision) -> batch UUID
postSales(batch_id, idempotency_key) -> posted/already-posted + latest balances
saveRecipe(menu_item_id, lines, revision) -> recipe version/current recipe
uploadInvoice(file, location_id) -> private file + invoice ID; async extraction later
saveInvoiceReview(invoice_id, fields, revision) -> validated draft
approveInvoice(invoice_id, revision) -> approved invoice only; no second receipt

SERVER RULES
Use NUMERIC for quantities/money and preserve decimal serialization at boundaries.
Validate inputs, tenant membership, supplier mappings, dates and duplicate refs.
Post whole documents atomically; lock rows; concurrent retries cannot double-post.
Prevent editing posted documents. Future correction uses explicit reversal entries.
Keep negative stock policy explicit; prototype allows it and flags reconciliation.
Historical sales details must read actual movements, not recompute current recipes.
Use pagination and loading/error/empty/retry states once remote requests exist.
Uploaded documents need allowlisted types, size limits, malware handling, retention
and private signed access; MIME/size checks in the demo are UX checks only.

This retains the supplied Supabase model rather than adopting another ERP backend.
